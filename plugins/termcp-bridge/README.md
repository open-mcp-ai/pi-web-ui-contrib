# 🖥️ termcp（pi-web-ui 插件）

把 [termcp](https://github.com/open-mcp-ai/termcp) 接进 pi-web-ui：

- **一个视图**：顶栏多一个 **🖥️ termcp**，点开是完整的 termcp 工作区（会话、标签、端口转发、审批队列）——它自己的界面，内嵌，不是复刻。
- **一套工具**：termcp 的 31 个工具（`session_*` / `shell_*` / `file_*` / `forward` / `message` / `ssh_config`）交给 AI，AI 就能开 SSH 会话、跑命令、传文件、开端口转发、推通知。
- **实例自动就位**：termcp 没在跑就自己拉起，已经在跑就接管，空闲 10 分钟后自行退出。你不用先手动起 termcp。

## 装

```bash
pi-web-ui install <本仓库>/plugins/termcp-bridge --force
```

或设置 →「界面插件」里从插件市场装。装完**刷新页面**，顶栏出现 🖥️ termcp。找不到就进 设置 →「界面布局」把它钉出来（新插件默认不钉在顶栏）。

需要 pi-web-ui ≥ 带了 `registerProxy` 的版本；termcp 需要 **v0.2.7 或更新**（页面 URL 按挂载前缀解析，见下面「为什么需要这个版本」）。

## 前置条件

- 装着 `termcp` 且在 `PATH` 里。不在时在插件设置里填绝对路径。
- 首次用某个远端会用到 termcp 自己的 SSH 凭据，那是 termcp 的事，本插件不碰。

## 设置

| 项 | 默认 | 说明 |
| --- | --- | --- |
| termcp 端口 | `18765` | termcp 监听的本地端口。改了这里，插件拉起的实例也用新端口。 |
| 代理挂载路径 | `/termcp` | 挂在哪个路径下，`/termcp` 对应 `http://localhost:8787/termcp/`。 |
| termcp 可执行文件 | `termcp` | 留空用 PATH 里的；不在 PATH 时填绝对路径。 |
| AI 工具接入方式 | `auto` | 见下。 |

### AI 工具接入方式（`auto` / `always` / `never`）

本插件给 AI 加工具，走的是 pi-web-ui 自带的 MCP 桥：往 `<数据目录>/mcp.json` 写一条 termcp 服务器，宿主热加载后把工具接上。这里有个**容易踩的双份问题**：

- 宿主桥注册的工具是**裸名**（`file_write`、`shell_input`）；
- 如果你另外用 pi 的全局 MCP 配置（`~/.pi/agent/mcp.json`、`~/.config/mcp/mcp.json` 等）也接了 termcp，那些工具会以**命名空间名**出现（`mcp__termcp__file_write`）。

两套同时存在 = 同一批 31 个工具出现两次，白吃一倍上下文。所以：

- **`auto`（默认）**：启动时扫一遍上面那些全局配置，**发现已经有人在提供 termcp 就不重复接**，日志里写明是哪个文件接手了，视图状态条也会标一句。它还会**撤回自己以前写的那条**（如果那次是它写的），因为此时那条才成了重复项。你手改过的条目不动。
- **`always`**：总是由本插件接。
- **`never`**：完全不碰 `mcp.json`，只要那个内嵌视图。

> 无头场景（比如只用 API 调 pi-web-ui）也照常走同一套：插件的 `activate` 是服务端代码，跟浏览器开不开无关。

## 它对你机器的改动（可逆）

只动一处：**`<数据目录>/mcp.json` 里的一条 `termcp` 服务器条目**。

- 首次写入前把原文件备份到 `mcp.json.termcp-bridge.bak`；
- 卸载时按备份**逐字还原**；原本没有这个文件就删掉（留一份 `.removed-<时间戳>` 副本以防万一）；
- 你手改过那条条目就**不再认领**，卸载时原样留着；
- 文件是坏的 JSON 时**一律不碰**，只提示一次。

进度、会话、SSH 凭据都在 termcp 自己的数据目录里，本插件不读不写。

## 为什么需要 termcp v0.2.7+

Web UI 以前假设自己挂在域名根：页面里 35 处 URL 是根绝对路径（`fetch('/api/...')`、WebSocket 的 `/api/ui/ws`）。把它放在 `/termcp/` 这种子路径反代后面时，页面本身能渲染，但这些请求会打到**父站点**上——表现为「界面在、数据空」，而且在根部署下永远复现不出来。

v0.2.7 起（提交 `apiPath()` 前缀解析）所有页面 URL 都按挂载前缀解析，所以反代下开箱可用。更早的版本里本插件的视图会是空的。

## 故障排查

**视图空白 / 一直提示「termcp 未响应」**

1. 状态条会显示端口和错误原因。先手动验一下：`curl http://127.0.0.1:18765/api/version`。
2. 起不来且报找不到命令 → 设置里填 `termcp` 的绝对路径。
3. 端口被别的东西占了 → 换个端口，挂载路径跟着调。

**视图是空的，但 `/api/version` 明明是通的**

termcp 版本低于 v0.2.7。升级它，或者把 pi-web-ui 的代理前缀设成 `/`（前提是 pi-web-ui 就挂在根）。

**AI 看不到 termcp 工具**

- 接入方式是 `never` → 改成 `auto`。
- 是 `auto` 且日志说「已经被某文件接手」→ 工具其实有，只是走的是那份配置；在**新对话**里看（宿主的工具注入发生在建会话时，改配置不会追溯已有会话）。
- 改了 `mcp.json` 后没生效 → 宿主是热加载的，但**工具表要新建对话才刷新**。

**卸载后 `mcp.json` 里还有 termcp**

那就是别人（你自己的全局配置）写的，不是本插件。

## 自测

```bash
node selftest.mjs
```

41 项，不需要宿主、不需要网络、不需要装 termcp。它用一个假 host 驱动真实的 `activate()`，钉住三类容易写错又看不见的事：反代挂载与注销、`mcp.json` 的精确改动与还原、`auto` 模式的让位与撤回。包含两个真实踩过的坑的回归用例：

- 用 6 字段 cron 注册定时器会让 `schedule()` 抛错 → 整个 `activate()` 失败 → 宿主回卷 effect 栈把反代一起注销（症状：`mcp.json` 写进去了，`/termcp/` 却是 404）；
- 卸载/让位时按「是不是我们写的」判断归属，否则会删掉用户手改的那条。

## 实现说明

- **视图用 iframe**：termcp 前端是一整个终端工作区，复刻它等于再维护一个会漂移的实现。iframe 地址从插件 bundle 自身的 URL 推导，所以 pi-web-ui 自己挂在 nginx 子路径下也对。
- **不注册 AI 工具**：pi-web-ui 的插件 API 没有 MCP 能力（`host.registerAgentTool` 只收 JS 函数），而宿主已经有一条完整的 MCP 通道（握手、失败隔离、子进程自愈、热重载、工具门控）。复用它是唯一不用重写一遍 MCP 客户端的做法。
- **不管 termcp 的停止**：一个拿走 SSH 凭据、还有独立 Web UI 的服务的生命周期属于用户。插件能拉起实例、并给它一个空闲倒计时（只对**它自己拉起的**实例生效，你手动起的不会被它停掉）。
